## Invariants observed (doctrine candidates)

- **Health is computed, never cached** (D3): the console derives system state live from every subsystem each time; only success results of expensive probes are cached (D8). A stale heartbeat is explicitly NOT an error — absence of a subsystem is a normal mode.
- **Training exclusivity is enforced twice** (thread mutex + cross-process file lock, NN-02) — the strongest mutual-exclusion posture in the codebase, matching how destructive the failure would be (two trainers clobbering checkpoints).
- **Integrity checks must never block the app**: 16 GB monolith ⇒ liveness probe at boot, quick_check only async with timeout, indeterminate reported as None rather than guessed (DG-02/R3-H07).
- **Every lifecycle transition is observable**: correlation IDs, CoachState status writes, error codes (CO-01..04), user notifications for missing optional deps (Docker WR-13).
- **Recovery is bounded and biased safe**: supervisor 3 restarts/hour; stuck ingestion tasks recovered only when provably stale (5 min) and only 3 times; manual stop always wins over auto-restart.
- Path-confinement checks at every filesystem output seam (RG-01, VZ-02, telemetry filename sanitization) — write paths are validated even against the project's own config/JSON.
- The "not wired" honesty pattern: server.py declares its own dormancy in the docstring instead of pretending to be integrated (same family as win_probability's "DORMANT BY DESIGN").

## Risks / open questions carried forward

- Console boot's belief-confidence tiers (0/50/80/100 at 0/1/50/200) and coach_manager's maturity tiers (CALIBRATING<50, MATURE, multipliers 0.5/0.8/1.0) and coaching_service's JEPA ladder (50/200) are three parallel maturity ladders keyed to match counts — same idea, three encodings; doctrine should name ONE maturity SSOT.
- ingest_manager's task claim (SELECT first → set processing) is not the F-0037 atomic-claim idiom used by run_worker — safe today only because a single manager thread drains the queue; flag if a second consumer ever appears.
- analytics `_player_filter` returns `(True,)` in pro-overview mode — `get_skill_radar` however filters by player_name only (no is_pro guard, no fallback), an inconsistency in fallback coverage between dashboard widgets.
- MatchVisualizer default `output_dir="reports/assets"` is CWD-relative while report_generator anchors to USER_DATA_ROOT — the DA-RG-01 confinement fix did not reach the visualizer's default.
- server.py + telemetry_client form a client/server pair that is dormant on both ends; if ever wired, the R4 telemetry contract test (202, player_name) must become CI.
